### analyzer-006 — A declared public surface is exempt from dead-code reporting, which cannot distinguish an SDK from an app

`analyzer` · low · confirmed

`get_user_agent` in `src/devopness/client_config.py` is listed in that module's
`__all__` and used within the module, but no internal module imports it. It is
public API of a published SDK, so its reader is a consumer outside the
repository and the absence of an internal import is the expected case.

The current rule exempts any module with a declared surface, which is correct for
a published package and too permissive for an application whose `__all__` merely
lists internal helpers. Distinguishing them needs `private` from each
`package.json` threaded into the analysis, and the false-negative cost is lower
than the false-positive cost that motivated the exemption. Recorded rather than
fixed because the current rule errs in the safe direction.


Not being fixed because: Erring toward missing a finding is preferable to telling maintainers to delete
their own public API, which is what the previous behaviour did.

### gate-001 — Power of Ten rule 10 is not enforced, and two specs claimed it was

`analyzer` · high · confirmed

`vp check` prints lint warnings and exits zero. As measured, seven pass: four
`no-unsafe-declaration-merging` in
`packages/sdks/javascript/tests/MergeSiblingClasses.spec.ts` and three in
`ui-react` (two `no-unused-vars`, one `no-unused-expressions`).

Two specifications asserted the opposite. `typescript.toml` carried
`warnings_are_errors = true`, and `power-of-ten.toml` said rule 10 was "already
enforced by `turbo run lint` and `turbo run typecheck`". Both were false, and
they agreed with each other, which is what made the gap invisible: reading
either spec confirmed the other. Nothing was checking.

Corrected to the measured value in both specs, and rule 10's `[not_gated]` entry
now states the count and what enforcing it would take.

The four sdk-js warnings are in a test that exercises declaration merging
specifically: `class Duck {}` merged with `interface Duck extends Flying,
Swimming {}`. The rule warns because the compiler cannot prove the merged
properties are initialised, but only methods are merged, so there is nothing to
initialise. That is an argument for a scoped suppression with a reason, not for
turning the rule off, and not for silencing the count.

Rule 10 is only half the story. Declaration emit is a second gap in the same
rule: `vite-plugin-dts` reports TS2883 for `Radio.styled.tsx` and continues, so
`turbo run build` succeeds while logging errors. Tracked as `build-002`.


Not being fixed because: Recorded rather than fixed. Each of the seven needs a judgement about whether it
is a real finding, and three of them are unused symbols that may be intentional
API surface, which is the same question as `dead-001` through `dead-004`. Making
the linter fail on warnings before those are settled would block every build in
the workspace over findings nobody has read.

### pot-001 — The one Power of Ten empty-handler finding is a deliberate, documented choice and should be accepted rather than changed

`dead-code` · low · confirmed

`pot7_empty_handler` reports one site:
`packages/sdks/python/src/devopness/core/api_error.py:66`.

```python
except json.JSONDecodeError:
    pass  # Keep self.message as-is
```

This is intentional and self-documenting. The surrounding code has already
extracted `self.message` from the exception, and when the response body is not
JSON there is nothing further to read, so the previous message is the correct
value to keep. The alternative, re-raising, would change the behaviour of a
shipped SDK for no gain.

The rule is mechanically right and the code is defensible, which is the case
`[[exception]]` exists for: a reason and an expiry. It should not be "fixed" by
deleting or rewriting a handler that works, and it should not be silenced by
relaxing the rule, since a no-op handler with no explanation is exactly what the
rule is for.


Not being fixed because: Left unfixed on purpose. A reviewer should accept it with a reason, or change
the code deliberately, but should not be pushed into editing correct library
behaviour to satisfy a gate. Expiry recorded so the acceptance is revisited.


Location:

- `packages/sdks/python/src/devopness/core/api_error.py`

### test-001 — Every test is recorded as deterministic because the generator writes true, not because anyone checked

`analyzer` · medium · confirmed

`testgraph.rs` sets `deterministic: true` unconditionally, in both the manifest
builder and the record generator. All 73 entries in `testing/tests.toml` carry
`deterministic = true` and not one is `false`.

`testing.toml` described the opposite: "Determinism is asserted by a human, not
inferred", with `determinism_is_asserted = true`. Nothing had been asserted. The
field is optimistic by default and therefore carries no information, so a test
that reaches the network, reads a clock or depends on randomness is
indistinguishable in the manifest from one that is genuinely deterministic.

The field is not decoration. It is the basis on which an affected run may reuse
a cached result, so a falsely deterministic test makes a cached pass mean less
than it appears to.

Corrected in the spec to `determinism_is_seeded_optimistic = true` and
`determinism_is_asserted = false`, so the record no longer claims a review that
did not happen.

The real fix is behavioural: `tetanus test generate` should preserve an existing
`deterministic` value rather than overwrite it, so a human marking a test
non-deterministic is not undone by the next regeneration. That change is not
made here.


Not being fixed because: Recorded rather than fixed because preserving the field means changing what
`test generate` writes, which affects the manifest's derived-from-the-graph
guarantee: `target` and `affected_by` are legitimately derived, but `deterministic`
is a judgement and mixing the two needs a decision about which fields the
generator owns.


Location:

- `.tetanus/specs/testing.toml`
- `testing/tests.toml`
- `tools/tetanus/crates/tetanus/src/testgraph.rs`

### analyzer-003 — Python relative imports never resolved, so the whole Python module graph was empty

`analyzer` · high · refuted

`resolve_internal` split the specifier on `/` and treated a `.` segment as a
no-op. A Python level-1 import is a single segment, `.base_service`, so the dot
stayed glued to the name and it resolved to `base/.base_service.py`, which does
not exist. Worse, Python separates package levels with dots rather than slashes,
so `from ..core.api_error import x` is one segment, `..core.api_error`, and had
to become two path segments.

Consequence: none of the 1482 relative Python import statements resolved. The
Python half of the graph had no fan-in, no fan-out, no reachability and no
affected-test precision, while still reporting success.

Surfaced as refuted reports for `DevopnessBaseService`, `DevopnessBaseServiceAsync`
and `DevopnessClientState`, all re-exported by `src/devopness/base/__init__.py`
and all with 54 and 5 real references.

Fixed by handling dot-prefixed segments in one place, and by adding a dotted
index built in a single pass so absolute imports such as
`from devopness.core.api_error import x` resolve in constant time.


Location:

- `tools/tetanus/crates/tetanus/src/workspace.rs`

### analyzer-004 — Python has no export keyword, so module-private helpers read as unused public exports

`analyzer` · high · refuted

`exported` was computed as "module level and not underscore-prefixed". That is
the only signal available without `__all__`, but it is wrong for any module that
declares its public surface, and it is wrong for TypeVars.

`T` in `src/devopness/core/response.py` is a `TypeVar` used as the parameter of
`class DevopnessResponse(Generic[T])` in that same file. Its `__all__` is
`["DevopnessResponse"]`, which does not include it, so the module had said
outright that `T` is not public and the analysis disagreed.

Also produced `debug_request`, `debug_response`, `is_access_token_expired` and
`is_token_change_request`, all module-private helpers used only by their own
module.

Fixed by reading `__all__` when present and treating a module that declares it as
having a stated surface. A computed `__all__` is deliberately not followed: a
name that cannot be read statically is not evidence either way, and guessing
would put private names back into the public surface.

### spec-001 — No check compares the subsystem specs against the implementation, so they drift silently

`analyzer` · high · confirmed

`.tetanus/specs/*.toml` is the declared contract for twelve subsystems. Nothing
verifies it. `living check`, `bugs check` and `classify` all have drift checks;
the specs have none, so a spec is only as true as the last time somebody read
it against the code.

Auditing all twelve found these, none of which any check would have caught:

  * `cache.toml` stated the parse key was content plus parser version. It is
    content, version and a context digest covering package layout, the generated
    registry and the tracked-file list. A correctness claim, and wrong.
  * `graph.toml` promised twelve node kinds. Five are emitted; `function`,
    `test`, `task`, `metric`, `ratchet` and `decision` are created by nothing.
    It also listed ten edge kinds where the builder inserts five.
  * `python.toml` listed `no_global_mutable_state` as enforced. It is not
    implemented. It also had `import_cycles` pending "needs the module graph
    extended to Python package boundaries", which was done: a dotted index now
    resolves both `from ..core.api_error import x` and `from devopness.core
    import y`, and cycle detection is live for Python and finds none.
  * `testing.toml` said determinism "is asserted by a human, not inferred" with
    `determinism_is_asserted = true`. The generator writes `deterministic: true`
    unconditionally and all 73 entries say so. Nothing was asserted.
  * `typescript.toml` said `warnings_are_errors = true`. The linter exits zero
    on warnings and seven pass.
  * `power-of-ten.toml` said rule 10 was already enforced, in agreement with the
    typescript spec, which is how the gap stayed invisible.
  * `ratchet.toml` said there were exactly three ways a baseline could change
    and listed fifteen metrics, omitting all eight Power of Ten ones and
    listing `complexity` as pending while a baseline gated on it.

Seven of the eight were written or changed in this same piece of work, which is
the sharper point: a discipline that only catches drift when somebody thinks to
look is not a discipline, and every one of these was found by reading, not by a
tool failing.

Fixed by `tetanus specs check`, in the check set between `classify` and `ast`.
What it enforces, all of it mechanically decidable:

  * every spec parses, and declares a non-zero version and a subsystem name
  * subsystem names are unique across specs
  * every gated metric is declared in some spec, and every spec that claims a
    gate has a baseline for it
  * no rule a spec declares as not gated has a baseline
  * the Power of Ten thresholds equal `tetanus_ast::power::Limits::default()`
  * the node and edge kinds a spec claims match the kinds the graph builds, and
    the kinds a spec records as absent or unused are still absent or unused

The node and edge check compares the spec to the built graph, not to the enum
definitions. `NodeKind` declares eleven kinds and the graph builds five, so a
check against the definitions would pass a spec claiming six that cannot exist,
which is the exact failure that was found.

Each check was verified by reintroducing the drift it exists to catch: a node
kind the graph does not build, a threshold changed in the spec only, a gated rule
declared as not gated, a kind recorded as absent that the graph now builds, and
a version of zero.

Building it found two further defects in the check itself. The `nodes_absent` and
`edges_defined_but_unused_here` lookups searched for top-level tables, but those
keys live inside `[nodes]` and `[edges]`, so both checks were silently inert
before a unit test caught them. And `[metrics]` is overloaded across the specs:
`ratchet.toml` writes `name = { direction, unit }` and `security.toml` writes
`name = "a description"`. Reading only the first shape would have made the check
ignore `security.toml` entirely, which is the opposite of what a drift check is
for.


Not being fixed because: The check covers only claims that are mechanically decidable. A spec that says a
rule "should" be written, such as a cyclomatic complexity metric, is
documentation and is not checked, because nothing would fail if it were never
written.


Location:

- `.tetanus/specs`
